# X3 协议笔记（只读事实与实现约定）

本文区分三种信息：**实测事实**（本机抓包）、**上游声明**（引用的开源实现）、**未验证解释**。
实测原始日志在 `evidence/local/`（已忽略），脱敏结论在 `docs/evidence/`。

## 1. 链路

- 已配对且已连接的 `OPPO Enco X3`，SDP 服务 UUID `0000079A-D102-11E1-9B23-00025B00A5A5`，服务名 `ELNK`，RFCOMM channel 由 SDP 动态解析（2026-09-23 实测为 15；另有 `enco rcord` = `…079B…` channel 24）。
- 传输使用 IOBluetooth `openRFCOMMChannelAsync` + delegate，所有回调在主 run loop；不使用 POSIX Bluetooth socket。
- 本应用只在设备已连接时打开自己的控制通道，退出/失联只关闭本通道。
- 实测：打包为 `.app`（含蓝牙 usage description）后由 `open` 启动可稳定打开；裸 CLI 首次打开曾超时，原因未确认。

## 2. 帧格式（已实现）

```
AA len 00 00 cmdLo cmdHi seq payLenLo payLenHi payload
```

- `len = 7 + payload.count`（单字节，故 payload ≤ 248，整帧 ≤ 257）；cmd 与 payloadLen 小端。
- 请求 seq 从 `0xF0` 起递增；**响应回显请求的 seq**（实测 0xF0 → 0xF0）。
- 响应命令 = 请求命令 | `0x8000`（`0x010C` → `0x810C`）。
- 两条长度字段必须严格相等，否则整帧拒绝并按字节重同步；解析器支持拆包、粘包、前导垃圾。
- 依据：上游 `Transport/SppFrameCodec.cs` + 本机实测帧。

## 3. 已实测的回包（payload，非完整帧）

| 查询 | 响应 | payload | 解读 |
|---|---|---|---|
| `0x0100` | `0x8100` | `00 FF 77 7A EE E6 8F 8E 04` | status + 8 字节能力位图（**未逐位验证功能**） |
| `0x0103` | `0x8103` | `00 10 74 06` | PID = `067410`（3 字节小端） |
| `0x0105` | `0x8105` | `00 03 31 2C …` | status + n + UTF-8 CSV 版本串 |
| `0x0106` | `0x8106` | `00 02 01 64 02 64` | status + count + (id, raw)…：左右各 100%，**不含充电盒** |
| `0x0106` | `0x8106` | `00 03 01 E4 02 64 03 E4` | 一只入盒后：左 100% 充电、右 100%、盒 100% 充电 |
| `0x010C [01 01]` | `0x810C` | `00 01 01 08 00` | status + `01 01` + 位图小端 = **0x0008** |
| `0x010F` | `0x810F` | `00 04` | EQ id 4（设备回包名称：自定义） |
| `0x012A` | `0x812A` | `00 00` | 空间音效类型 0 = 关闭（耳机自身模式） |
| `0x0112` | `0x8112` | `00 03 …` | status + count + 条目：MAC(6 小端) + elem + connState + flag + nameLen + name(UTF-8) |
| 通知 | `0x0204` | `06 …` / `03 01 01 …` / `01 count …` | 子类型：`0x06` 多设备、`0x03` 降噪、`0x01` 电量（部分更新） |

电量规则（实测 + 上游一致）：`raw & 0x7F` = 百分比，`raw & 0x80` = 充电中；上报 `0` 或 `>100` 视为**未知**，不显示 0%。
`0x8106` 是完整响应，未返回的槽（如休眠的充电盒）清空为未知；`0x0204` 通知是部分更新，只改列出的槽。

## 4. 降噪位图（型号配置解释 + 实机验收）

来源：上游 `Data/DeviceModels.json` 的 `whiteList[114]`（对应 PID `067410`）`function.noiseReductionMode`
与 `DeviceProfileLoader.ModeKey`；**不套用 realme 的 legacy 交换**。
`bitmap` 是**发送值**，`aliases` 是设备可能回报的同义值。

| modeType → 名称 | 发送 protocolIndex | 发送位图 | 别名（父值） | 实机验收 |
|---|---|---|---|---|
| 1 → 关闭 Off | 3（子） | `0x08` | `0x01` | ✅ SET 8 → ACK 0 → 回读 8 |
| 2 → 通透 Transparency（固定子模式） | 8（子） | `0x100` | `0x04` | ✅ SET 0x100 → 回读 0x100（父值 0x04 会回读 0x200，非固定通透） |
| 7 → 智能降噪 Smart | 7 | `0x80` | — | ✅ |
| 4 → 深度降噪 Deep | 4 | `0x10` | — | ✅ |
| 8 → 中度降噪 Medium | 5 | `0x20` | — | ✅ |
| 3 → 轻度降噪 Light | 6 | `0x40` | — | ✅ |
| 6 → 自适应通透 Adaptive | 9 | `0x200` | — | ✅（独立档位，绝不判为通透成功） |
| 5 → NC（父模式） | 1 | `0x02` | — | 面板不提供 |

- 七个候选值均由应用经 IOBluetooth 逐项实测：精确 ACK + 精确回读，最后恢复原始位图 `0x08` 成功
  （见 `docs/evidence/2026-09-23-anc-verified.md`）。因此 ANC 按钮默认可用，不再需要开关参数。
- 首轮 `cycle-anc`（`docs/evidence/anc-first-cycle.md`）发现父值会被归一化：写 `1` 回读 `8`，写 `4` 回读 `512`，
  故发送值改用子值；恢复按**捕获到的原始位图**原样写回。
- 以上验证的是协议写入与状态读回；模式名称依型号表，未做声学或人工听感判定。

## 4b. EQ 与空间音效（实测回包）

| 查询 | 响应 | payload | 解读 |
|---|---|---|---|
| `0x010F` | `0x810F` | `00 04` | 当前 EQ 预设 id（4 = 设备侧自定义） |
| `0x0122 [01 05]` | `0x8122` | `00 01 01 FA 06 04 09 E8 87 AA E5 AE 9A E4 B9 89 06 3E 00 FD FA 00 01 E8 03 01 A0 0F FE 40 1F 02 80 3E 02` | status + count + 条目：`[isSelected][minSigned][maxSigned][eqId][nameLen][name][freqCount][freqLE16+gainSigned]×n` |
| `0x012A` | `0x812A` | `00 00` | 空间音效类型：0 关闭 / 1 固定 / 2 跟随（耳机自身模式） |

- 实测 `0x0122` 只返回 **count=1** 的自定义预设（id 4，min -6 / max 6，频点 62/250/1000/4000/8000/16000 Hz，
  增益 -3/1/1/-2/2/2 dB）——它**不是**内置预设全表。
- 增益按**有符号字节**解析；解析要求精确消费整帧，长度/UTF-8/段数任一不符即整帧拒绝并保留原始 payload。
- 内置预设名称（0 至臻原音、1 高清解析、2 纯享人声、3 澎湃低音、7 丹拿特调）来自上游 X3 配置，
  设备回包里有名称时以设备名优先；日常 UI 显示名称，来源记录保留在文档与 CLI。

## 5. 写命令（本阶段允许的三条）

允许集合（`EncoCommand.allowedWriteCommands`），其余命令在发送前即被拒绝：

| 命令 | payload | 回读命令 | 成功判定 |
|---|---|---|---|
| `0x0404` 降噪 | `[01, 01]` + 最短小端位图（`0x08 → 01 01 08`、`0x100 → 01 01 00 01`、`0x200 → 01 01 00 02`） | `0x010C [01 01]` | ACK status=0 且回读位图 == 目标 |
| `0x0406` EQ 预设 | `[id]` | `0x010F` | ACK status=0 且回读 id == 目标 |
| `0x0422` 空间音效 | `[type]`（0/1/2） | `0x012A` | ACK status=0 且回读 type == 目标 |

- 三条写命令共用同一套规则：单事务在飞、有限超时（4s）、写入后 0.2s 起轮询回读（预算 4s）、
  **无 status 字段的 ACK 一律失败**；设备把值归一化成已知别名时报 `normalized`（降噪），其余不一致报 `readbackMismatch`。
- 明确不写：自定义 EQ 曲线（只切换预设 id）、多设备/优先设备相关命令、codec，以及所有其它 SET。

## 6. 未验证 / 待确认

- 7 种降噪、EQ `[0,1,2,3,7,4]`、空间 `[1,2,0]` 均已实机 ACK + 精确回读验证，并恢复原值。见 `2026-09-23-audio-verified.md`。
- 降噪/EQ 未做声学测量；空间跟随已有用户转头听感确认，见 v030 验收记录。
- 内置 EQ 预设名称与曲线的对应（上游配置，未实测）；设备当前只返回自定义预设 id 4。
- 固定/跟随在 Mac 人声对比中出现用户可辨别的前方声源稳定效果；无延迟、角度精度测量或原始姿态流。
- 多设备条目的 `elem`/`flag` 语义来自上游解释，只有 `connState`（0/1/2）和名称经过结构校验。
- 能力位图（`0x8100`）中未声明多设备操作 `0x0429` 与优先设备查询 `0x0132`，因此双设备保持只读。
